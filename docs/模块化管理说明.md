# 模块化管理说明

本次整理于 2026-10-06 完成结构调整，沿用原有插件协议、启动方式、HTTP 接口和行程存储格式。模块按业务职责划分；运行数据、配置、注册文件和历史日志不参与源码整理。

## 项目边界

| 目录 | 职责 | 管理规则 |
| --- | --- | --- |
| `core/` | 插件宿主、安装、进程管理、控制台，以及现有跨模块纯计算 | 共用计算放在这里；具体模块的 HTTP 路由放回所属模块 |
| `contracts/` | API/数据契约、运行时协议、生成产物 | 修改源契约后运行生成器；不手改 generated 文件 |
| `modules/<id>/` | 一个独立运行的业务模块 | `manifest.json` 声明依赖，`plugin.py` 负责启动与释放资源 |
| `web/` | 管理控制台页面 | 与行程工作台的 `modules/web_workbench/web/` 分开维护 |
| `tests/` | 核心、跨模块集成及页面接线回归 | 测试需要通过真实入口加载；避免复制一份过期的资源加载表 |
| `modules/<id>/tests/` | 模块自身测试 | 测试所属功能，使用临时工作目录 |
| `tools/` | 数据自检与验收命令 | 从文件位置定位项目根目录，不依赖调用时的工作目录 |
| `modules/<id>/data/` | 随代码交付的只读主数据 | 数据与代码一起交付；与根目录 `data/` 的运行数据区分 |
| `config/`、`data/`、`logs/` | 用户配置、运行数据与日志 | 禁止当作构建缓存清空，整理源码时保留 |
| `.staging/`、`.trash/` | 安装暂存与卸载存档 | 由管理器负责维护 |

模块间仍按 `contracts/MODULE_RUNTIME.md` 使用本地服务与注册表通信。模块内部优先使用相对导入，例如 `from .service import TripService`，避免不同模块的 `engine.py`、`store.py` 或 `proxy.py` 通过全局名字互相抢占。宿主将 `plugin.py` 作为包入口加载，支持这样的导入方式。

## 行程引擎 `modules/trip_engine/`

| 文件 | 职责 |
| --- | --- |
| `plugin.py` | 从 Context 读配置，建立服务，登记端口，协作退出并释放资源 |
| `engine.py` | 原有接口的兼容导出；保留 `TripService`、`build_server`、`serve` 等名字 |
| `service.py` | 行程创建、预校验、读取、修改、复制、删除与统一提交 |
| `validation.py` | 锚点、预算、费用和每日锚点输入校验 |
| `stops.py` | 添加、排序、移除、跨天/晚间移动，日状态和路线失效处理 |
| `recommendations.py` | 推荐骨架预览、完整方案校验、原子创建与补空白日 |
| `catalog.py` | POI、口岸和住宿候选的只读查询 |
| `domain.py` | 枚举、时间单位、断言、同一行程的事务装饰器 |
| `errors.py` | 业务错误的状态码、错误码、消息与详情 |
| `store.py` | 行程单文件存储、原子写和 POI 主数据读取 |
| `http_api.py` | 令牌鉴权、HTTP 路由、响应信封和服务器生命周期 |
| `poi_seed.py` | 汇总两批 JSON 景点，保留原有 `POIS` 列表接口和顺序 |
| `anchors_seed.py` | 口岸与住宿 JSON 加载及缓存 |
| `data/shanghai_pois_v1.json` | 原有 25 条景点种子数据，完整保留原字段与值 |
| `data/shanghai_pois_v2.json` | 第二批 20 条景点数据 |
| `data/poi_description_reviews.json` | 45 条景点简介的事实来源与编辑建议边界，独立于运营资料审核 |

`TripService` 是统一对外的应用服务。它通过职责明确的内部 mixin 复用校验、停靠点、候选查询和推荐写入，自己统一持有存储、时钟和事务锁。mixin 不应单独实例化；停靠点操作通过 `_commit` 提交，由同一套锁保护读改写，避免拆文件后丢失原子性。HTTP 层依赖业务服务，业务服务不依赖 HTTP 层。

新增一个行程编辑操作时，将操作放在对应业务文件，再在 `http_api.py` 添加端点映射。新增或调整景点条目时修改对应 JSON，并运行数据与坐标检查；数据可信度和来源说明保留在 `poi_seed.py` 与审核记录中。

景点简介使用 POI 契约的可选 `description_zh`（1～120 字），随 `/pois` 返回。更新简介不变更运营可信度、行程存储或推荐方案契约；前端按 POI ID 查询主数据，旧行程自动显示最新简介。外部或旧版 POI 缺少字段时由页面统一提示。

## 工作台 `modules/web_workbench/`

后端的 `engine.py` 负责静态资源与代理路由，`proxy.py` 负责服务发现和上游调用，`map_config.py` 负责底图配置和 CSP。`currency_rates.py` 独立处理固定币种的联网参考汇率、超时、校验及缓存；工作台接口鉴权后调用它。`engine.py` 继续导出 `map_config`、`build_csp`，兼容既有调用。

前端保留原生 JavaScript 与零构建部署方式。各功能脚本通过现有函数接口协作，共享状态集中在 `runtime.js`，不在每个文件重新创建状态或会话。它们仍是按序加载的经典脚本，尚未改为 ES Modules。

| 脚本 | 职责 |
| --- | --- |
| `runtime.js` | 唯一的共享状态、会话、API 请求、DOM 工具与时间格式化 |
| `poi_content.js` | 景点简介读取、去除首尾空白与缺失值提示；四处展示共用 |
| `services.js` | 引擎健康状态展示与刷新 |
| `anchors.js` | 口岸/住宿加载、统一搜索、已保存住宿兼容及坐标匹配 |
| `setup.js` | 表单读取/回填、创建/保存/回滚、默认值与草稿 |
| `recommendations.js` | 日期勾选、生成与保存编排、推荐解释及模块降级 |
| `itinerary.js` | 行程概览、当前天、停靠点预检与编辑 |
| `poi_list.js` | POI 筛选、排序与列表 |
| `poi_details.js` | 景点详情字段映射与抽屉 |
| `map_view.js` | 示意地图与真实地图装配、提示和图钉刷新 |
| `map.js` | 地图 SDK、坐标转换、图钉与图钉状态 |
| `flow.js` | 历史行程、规则求值、路线计算和离线包的流程编排 |
| `offline_view.js` | 离线预览与独立 HTML 导出，四语界面与问路句、站口/步行/终点交通展示及旧快照提示 |
| `i18n_catalog.js`、`i18n.js` | 工作台语言字典、偏好保存、设置入口和语言变更通知 |
| `day_points.js`、`day_cards.js` | 每日锚点解析与日卡渲染 |
| `navigation.js` | 每日导航交互 |
| `reminders.js` | 行程提醒 |
| `currency.js` | 外币预算输入换算、显示偏好、参考汇率与手动汇率、草稿币种上下文 |
| `budget_assessment.js` | 折叠预算评估与人民币费用编辑，保护未保存输入 |
| `app.js` | 页面事件装配和 `boot()` 启动入口 |

`index.html` 是实际加载顺序的来源：`runtime.js` 最先加载，`poi_content.js` 在简介消费者之前加载，原有 SDK/流程脚本与功能脚本随后加载，`app.js` 最后启动。所有脚本均使用 `defer`；文件加载阶段只定义函数和状态，DOM 操作与请求由启动入口或事件触发。功能之间可以在函数体中调用另一文件的函数，但不得在加载阶段调用尚未加载的文件。

新增脚本时必须同时登记到后端 `engine.py` 的 `ASSETS` 和 `index.html`。修改前端资源后，统一更新 HTML 中所有 `?v=` 版本号，避免浏览器混用新旧文件。页面接线与详情测试通过 `tools/workbench_assets.cjs` 读取真实 HTML 和挂载表，自动沿用当前加载顺序。验收模拟服务 `tools/verify_soft_utility.cjs` 也复用同一挂载表，不再单独维护资源清单。

## 验证与维护

在项目目录运行一次完整验证：

```powershell
python tools/verify_project.py
```

该命令从自身位置确定项目目录，依次运行核心 Python 测试、四个服务模块的测试、所有 `tests/*.test.js`、契约校验、运行时自检、生成产物同步检查和启动器 `--list`。各组使用独立进程，有任何失败时返回非零退出码。环境需要 Python、Node.js；完整结构校验使用可选依赖 `jsonschema`。

## 推荐模块 `modules/recommendation_engine/`

`planner.py` 只计算建议，`client.py` 按请求读取行程引擎，`service.py` 装配输入与响应，`http_api.py` 负责鉴权与标准信封，`plugin.py` 负责依赖等待及服务登记。模块声明硬依赖 `trip_engine`，工作台把推荐模块列为可选依赖；推荐不可用时，原有手动编辑仍可使用。

闭馆日期与例外的纯判定放在 `core/poi_availability.py`，由规则模块和推荐模块共同调用。推荐器不直接导入其他插件的实现，不直接读写行程文件；保存通过行程引擎的事务接口进行。理由、估算时间与待核验提示仅在推荐响应中展示，持久化仍使用原有可编辑停靠点结构。

针对模块加载边界的快速检查：

```powershell
python -m unittest discover -s tests -p test_module_loading.py
node tests/workbench_wiring.test.js
```

源码整理的回归检查还应关注：行程版本冲突、同一行程的并发修改、跨天移动、路线失效、草稿恢复、API 鉴权与引擎未就绪时的降级展示。现有测试覆盖这些行为。

受限 Windows 沙箱可能使 `TemporaryDirectory` 的目录 ACL 无法写入；若测试在 setup 中报 `PermissionError`，应使用普通 Windows 权限运行验证。不要为此改动业务代码或把绕行配置加入交付文件。
