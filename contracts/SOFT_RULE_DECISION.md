# 决策简报：软规则能不能自己改行程顺序？

> ## ✅ 已决策（2026-09-25）：**方案 A —— 软规则只出提示，改单必须由用户显式触发**
>
> 落进契约的内容：`rules.json#/execution_model/iteration_policy`（`auto_apply_soft_rules: false`、`max_iterations: 1`、`order_mutation_allowed` 白名单）、`rules.json#/execution_model/soft_rule_decision`、`rule_02_lightup` 的 `on_action.move_to_evening`（含 `on_still_failing` 与 locked 语义）、新增文案 `rule.lightup.still_early`、AC-R2-04~07。
> 本文以下内容保留为决策依据存档；方案 B/C 的代价分析仍然有效，将来若反悔可据此重评。

> 对应 C3 契约中「软规则是否改排序」一条。
> 涉及规则：Rule-02 亮灯时序（唯一带「改单」动作的规则）；间接受影响：Rule-03 地理跨度、Rule-04 同质化。
> 一句话：这不是技术难题，而是**一个产品取舍**——「少一次点击」还是「指标可达 + 行为可预期」。

---

## 1. 先说清楚这个决策到底在决定什么

PRD 3.3 的 Rule-02 给了用户一个快捷操作：`[Move to Evening]`，一键把 POI 挪到晚餐后或当日末位。

要决策的不是「要不要这个按钮」（按钮肯定有），而是：

> **系统在判定「这个点该挪到晚上」之后，能不能自己动手挪？**

- 若能自己挪 → 点会跳位置，用户什么都不用点，但**顺序会被系统改动**，而顺序一变，时间轴要重算，重算后规则可能又被触发。
- 若不能自己挪 → 系统只提示，用户点一下按钮才挪。

关键在于：**PRD 没写这一条**。它给了按钮，也写了「建议」，但没说建议是被自动执行的还是等用户点。三个开发如果各理解一套，C 会写出一套会自动改单的引擎，A 会做出一套等用户点击的界面，联调必然对不上。

## 2. 用外滩这个真实场景走一遍

设定：夏季窗口 `19:00 - 23:00`，`T_light = 窗口起点 - 30 分钟 = 18:30`（见 `mappings.json` / `poi.schema.json` 的 `T_light_rule`）。
当天已排：酒店 → 上海博物馆（14:00–16:00）→ 外滩。外滩预计 **17:40** 抵达。

### 方案 A：软规则只提示，改单必须由用户触发（当前契约草案）

```
17:40 抵达外滩预测 → Rule-02 判定 too_early（早于 18:30）
   ↓  只出提示（inline_bubble）
"建议 18:30 之后前往，夜景效果最佳。 [移到晚间] [忽略]"
   ↓  用户点击「移到晚间」
重排：酒店 → 博物馆 → 外滩 →（晚餐/末位）
   ↓  重算该日受影响区段
19:40 抵达外滩 → 不再早于 18:30 → 提示消失，规则收敛
```

- 系统**从不动用户的单**；顺序的每一次变化都对应一次用户的明确操作。
- 收敛是必然的：不自动改单，就没有「改单→重算→再改单」的回路。
- 代价：用户要多点一次。

### 方案 B：系统自动改单并重算（PRD 没排除的另一种读法）

```
17:40 抵达 → too_early → 系统自动挪到末位 → 重算 → 18:35 抵达（收敛）✅ 顺利情况
```

但自动改单会把自己变成触发器。看三个真实的退化场景：

**B-1 无法收敛（末位之后没有更晚的位置）**

```
当日已有 4 个点，外滩被挪到末位 → 得到"末位"这个位置本身
重算 → 22:50 抵达 → 仍在窗口内（< 23:00）但已近结束 → Rule-02 的 too_late 分支触发
→ 建议改天 → 改天又触发 Rule-01（那天可能闭馆）→ 再改回来 …
```

**B-2 振荡（两次改单互相打回）**

```
11:10 外滩 → 系统挪到末位 → 末位抵 17:40（因为末位其实就是傍晚）
→ 仍 too_early → 再挪 → 位置没变（已经是末位）→ 死循环
```

**B-3 联动放大（一次改单触发别的规则）**

```
外滩挪到末位 → Rule-03 重新计算相邻跨度（新邻点是浦东的点）→ 提示"长途移动"
→ 用户或系统又调整 → Rule-04 的同质化计数变化 → 又出 Banner
```

**所以方案 B 必须额外定义至少四件事**（都得写进契约，否则实现不了）：
1. 单次操作的**自动改单次数上限**；
2. **不收敛时的取舍**（保留哪个版本、是否回滚到用户原顺序）；
3. **是否允许改动 `locked` 的点**（用户手动固定的点）；
4. **自动改单是否算用户操作**——它要不要写进 `revision_history`、能不能被撤销（PRD 全文无撤销机制）。

### 方案 C：规则本身不动顺序，只换提示的呈现顺序

```
所有软规则照常求值，但输出的是"提示排序"而不是"行程排序"。
列表按 硬冲突 > 亮灯 > 跨度 > 同质化 分组展示，用户从上往下处理。
```

- 对行程数据零副作用，实现最简单，也最好测试。
- 代价：`[Move to Evening]` 这个按钮的语义变弱（它仍然是用户触发），产品承诺的「一键优化」体验打折。

## 3. 三个方案的代价对比

| 维度 | A：只提示，用户触发 | B：系统自动改单 | C：只改提示顺序 |
| --- | --- | --- | --- |
| 用户点击次数 | 多 1 次 | 最少 | 多 1 次 |
| 行为可预期性 | 高（系统从不擅自改单） | **低**（顺序会自己跳） | 高 |
| 实现复杂度 | 低 | **高**（要定上限、收敛、回滚、locked 交互） | 最低 |
| 可测试性 | 好（AC 可以写成确定性用例） | **差**（需要时序/迭代类用例） | 好 |
| 与 1.2s 指标的关系 | 不变（每次点击 1 轮重算） | **直接冲突**：迭代 N 轮 = N 倍三方调用；而契约里一次拖拽的调用预算是 ≤4 次、缓存 3 QPS 排队本身就 2–6s | 不变 |
| 与撤销机制的关系 | 天然可撤销（重排是一次用户操作） | **需要额外设计**（自动改单要不要进历史栈） | 天然可撤销 |
| 与离线包的关系 | 简单（快照即最终态） | 复杂（要固化"系统已自动调整过"的痕迹） | 简单 |
| 对产品卖点的影响 | 「一键优化」变成「一键+确认」 | 体验最顺，但风险最高 | 弱化最明显 |

## 4. 方案 A 的真实代价（要一起算进去）

选 A 不是没有成本，它必须多定义两条，否则按钮会变成 bug 来源：

1. **点击「移到晚间」后如果仍然不满足条件怎么办？** 例：当天只有 2 个点，挪到末位后抵达 17:45，依然早于 18:30。此时应当：
   - 接受结果并保留提示（提示"已移到末位，仍建议 18:30 后前往"）；还是
   - 拒绝移动并告诉用户"移动无助于解决该问题"。
   **契约里必须二选一**——`rules.json` 的 `on_action.move_to_evening` 需要补 `on_still_failing` 字段。
2. **`locked` 的点不能被移动**（契约已定：`locked: true` 的点是用户手动固定的）。那么"末位"的定义要明确为「最后一个**未锁定**的位置」。

这两条对 A / B / C 都需要，但只有 A 会把它们暴露在用户路径上，所以 A 的 AC 用例必须覆盖「移动后仍不满足」这一分支。

## 6. 我的建议（供你决策时参考，不代表已定）

**倾向方案 A**，理由不是技术偏好，而是两条硬约束：

1. **1.2s 指标**：契约已确认一次拖拽 ≤4 次三方调用。B 方案的迭代会把调用数乘上迭代轮数，而 PRD 的 1.2s 本身已经被评审判定为「在配额下不可达」——再叠一层迭代，这个指标就只能删掉。
2. **可测试性**：A 的每一条 AC 都是确定性用例（给了输入就有唯一输出）；B 需要写「时序类」用例，且"合理的不收敛行为"本身没有客观标准，测试和产品很难就"这样算不算对"达成一致。

如果最终一定要 B 的体验，建议**折中**：保留 A 的执行模型，但把「移到晚间」做成**显式的批量建议**——系统把当天所有"建议移到晚间"的点聚合起来，一次点击应用全部，并明确告诉用户改了什么（而不是静默逐个移动）。这样体验接近 B，但行为仍然可预期、可撤销、可测试。
